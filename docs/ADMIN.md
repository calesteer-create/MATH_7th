## 2. كيف تعمل اللوحة

```
public/admin/index.html   صفحة ثابتة: بانر «تجريبي»، شرح التوكن، ثم محرر Sveltia
public/admin/config.yml   مولَّد من src/media/cms-config.ts (لا يُحرَّر يدويًا)
```

### نقطة التركيب (mount point)

Sveltia 0.262.1 تُركَّب على `#nc-root` إن وُجد، وعلى `<body>` إن غاب:

```js
// services/api/methods/init.js — من مصدر الحزمة المثبَّتة
mount(App, { target: document.querySelector('#nc-root') ?? document.body, props: { config } });
```

- الصفحة تحمل `<div id="nc-root"></div>` **خارج** `<main class="notice">`، لأن
  المحرر يستبدل محتوى هدفه — فلو كان داخلها لابتلع بانر التحذير.
- المعرّف السابق `#cms-mount` **لا معنى له**: لا يظهر في الحزمة إطلاقًا، فكان
  المحرر يسقط إلى `<body>`. وتركيب `<body>` يغطّي الشاشة كلها ويضيف
  `body:not(:has(#nc-root)) { overflow: hidden }` (في `components/app.svelte`)،
  فكان البانر يُغطّى ويُقفل تمرير الصفحة. الآن `<body>` يحتفظ بتمريره،
  و`#nc-root > .sui.app-shell` بموضع `absolute` داخل صندوقه، فيبقى التحذير مقروءًا.
- شاشات أصغر من `40rem`: البانر يتمرّر بعيدًا ويأخذ المحرر الشاشة كاملة.
- **لا تهيئة يدوية**: وسم `<script>` كلاسيكي ينتهي بـ`/sveltia-cms.js` يُقلع
  تلقائيًا (`lib/main.js`). إضافة `type="module"` تُعطّل ذلك، و`CMS.init()` غير
  مستخدمة هنا. `tests/admin-config.test.ts` يثبّت هذا كله.

- الخادم (backend) هو `github`، والمستودع هو **مستودع المسودات الخاص**، وهو
  **مثبَّت**: `calesteer-create/MATH_7th-drafts` ولا شيء غيره.
  `DRAFT_REPO` صار بإمكانه فقط **إعادة كتابة الاسم نفسه** (حالة الأحرف، `.git`،
  شرطة زائدة)؛ أي مستودع آخر — ولو كان خاصًا في الواقع — يُرفض عند التوليد:

  ```
  ✗ refusing to generate the admin config: <repo> is not the agreed drafts
    destination (calesteer-create/MATH_7th-drafts) …
  ```

  السبب: اسم المستودع لا يُثبت أنه خاص، والمولّد يعمل بلا شبكة. تغيير الوجهة
  يحتاج تعديل كود + تحققًا حيًّا من GitHub (`npm run admin:verify-github`).
  عند الرفض لا يُكتب الملف إطلاقًا: `public/admin/config.yml` يبقى بايت-ببايت.
- المصادقة: **access token** فقط (`auth_methods: [token]`). لا يوجد OAuth worker
  منشور لهذا المشروع، ولا نطلب منك إنشاء واحد.
- `publish_mode: simple`: الحفظ يذهب مباشرة إلى فرع المسودات. لا يوجد
  editorial workflow ولا Pull Request تلقائي (يحتاج `pull_requests: write`).
- المجموعات المُعرَّفة: **الوحدات**، **الدروس** (مع قائمة الصور)، **إعدادات المنصة**.
  مجموعة الاختبارات أُزيلت من اللوحة في هذا الـPR لأن نموذج الاختبارات عميق
  (نسخ/أسئلة/أجزاء) وأهدافه ما زالت «للمراحل القادمة»؛ إبقاؤها بمحرر ناقص كان
  سيخالف قاعدة «لا تستبدل النموذج».

### الترتيب

`position` هو حقل ترتيب صريح في الوحدات وفي الدروس (كما يفرضه نموذج المحتوى
القائم، ولم يُستبدل). قوائم Sveltia تدعم الفرز بـ`position`، وتُظهر الدرس داخل
وحدته عبر حقل `relation` إلى مجموعة الوحدات. **لم يُفعَّل** سحب-وإفلات يعيد
كتابة `position` في ملفات متعددة: هذا يتطلب كتابة ذرّية عبر عدة ملفات، وهو ما
لا يضمنه Sveltia؛ إعادة الترتيب اليوم تعديل حقل واحد لكل عنصر (معاينة فورية،
وكتابة commit لكل حفظ).

### الحالات

- الوحدة: لا حالة نشر لها في النموذج (تظهر إذا كان فيها درس منشور) — لذلك لا
  تحمل حقل حالة، **ولا تحمل `view_groups`**: التجميع يفلتر بقيمة حقل، ولا حقل
  حالة/أرشفة موجود. (كان في الإعداد الأول `view_groups` يشير إلى `archived` غير
  المعرَّف؛ وهذا **خطأ قاتل** لا تحذير — انظر «التحقق من أسماء الحقول» أدناه.)
- الدرس: `status: draft | published`، و`publishedAt`، و`isLastInUnit`.
  «منشور» هنا **يعني جاهزًا للنشر في المسودات**، ولا ينشر شيئًا تلقائيًا.

## 3. كيف تُحفظ المسودات

```text
متصفحك  ──(PAT في localStorage)──▶  api.github.com  ──▶  MATH_7th-drafts (خاص)
                                                          content/units/*.json
                                                          content/lessons/*.json
                                                          public/media/lessons/<id>/*.webp
```

- كل حفظ = commit واحد على فرع المسودات، عبر
  `createCommitOnBranch(expectedHeadOid: …)` — نفس ما يستخدمه Sveltia.
- `expectedHeadOid` هو حماية GitHub من الكتابة المتزامنة: إذا تغيّر رأس الفرع
  بين القراءة والكتابة يرفض GitHub الـcommit بدل أن يطمس تعديلًا آخر.
- **لا شيء** في المسودات يؤدي إلى نشر عام: يوجد Workflow نشر Pages في المستودع
  العام، لكنه يبني من `main` العام فقط ولا يشير إلى المسودات ولا يقرأها
  (`tests/no-public-write.test.ts` يتحقق من ذلك بنيويًا).
- الصور المرفوعة من المتصفح تُحوَّل إلى WebP قبل الرفع
  (`media_libraries.all.transformations.raster_image.format: webp`)، وWebP
  لا يحمل حاوية EXIF/GPS، فالحذف بنيوي.

### الحد الذي لا يستطيعه المتصفح

Sveltia **لا يستطيع** حساب:

- `sha256` للملف المخزَّن،
- `width` / `height`،
- `thumb` (نسخة مصغّرة إلزامية لكل صورة في النموذج).

لذلك أي صورة تُرفع من المتصفح تُنتج سجلًا ناقصًا. الحل: شغّل بعد الحفظ

```bash
npm run media:sync            # يكمّل الناقص + يُنشئ المصغّرات + يتحقق
npm run media:sync -- --check # يفشل إن كانت الشجرة غير متزامنة
```

`media:sync` لا يحذف شيئًا أبدًا: يبلّغ عن الملفات اليتيمة (orphans) ويتركها
لك. وفي المقابل، خط الاستيراد المحلي (`media:import`) ينتج السجل كاملًا من
البداية.

## 4. استيراد الصور من جهازك

```bash
# 1) الأصل يبقى في مجلدك — لا يُنسخ إلى المستودع أبدًا
npm run media:import -- --lesson 3 --from ~/scans/lesson-3

# تجربة بدون كتابة
npm run media:import -- --lesson 3 --from ~/scans/lesson-3 --dry-run
```

ما يحدث لكل ملف، بالترتيب:

1. **فحص النوع من البايتات** لا من الامتداد (JPEG/PNG/WebP فقط؛ HTML أو PDF
   يُرفض).
2. **فحص الحجم** (15 MiB افتراضيًا) **والأبعاد** (بين 64 و20000 بكسل، وأقل من
   120 ميجابكسل — حماية من قنابل فك الضغط) *قبل* فك الترميز الكامل.
3. **تصحيح الدوران**: تُطبَّق `EXIF orientation` على البكسلات أولًا (`.rotate()`)،
   ثم يُهمَل EXIF كله — فلا تخرج صفحة مقلوبة ولا إحداثيات GPS تخرج معها.
4. **ترميز WebP**: نسخة ويب ≤2200px (الجودة 84) ونسخة مصغّرة ≤480px (الجودة 70)،
   بلا ICC وبلا XMP.
5. **اسم ملف آمن وحتمي**: `^[a-z0-9][a-z0-9-]{0,60}\.webp$` — بلا مسافات، بلا
   حروف كبيرة، بلا `/` (فلا هروب من المجلد بنيويًا).
6. **منع التصادم**: محتوى مطابق (نفس sha256) → إعادة استخدام الاسم (استيراد
   متكرر لا يُنشئ `page-01-2.webp`). محتوى مختلف بنفس الاسم → `page-01-2.webp`.
   وكل كتابة تستخدم علم `wx` فلا يُستبدل ملف قائم أبدًا.
7. **تحديث ملف الدرس** بالحقول المشتقة (الموضع، الاسم، الأبعاد، sha256).
8. **لا حذف**: الصور القديمة التي لم تعد في الدرس تُبلَّغ فقط.

### حذف السجلات من المحرر

`delete: false` في مجموعتَي الوحدات والدروس خيار **مدعوم وموثّق** في
`@sveltia/cms@0.262.1`، لا زخرفة:

```yaml
# مخطط الحزمة (schema/sveltia-cms.json → EntryCollection.properties.delete)
delete:
  type: boolean
  description: Whether to allow users to delete entries in the collection. Default: `true`.
```

والوقت التشغيلي يحترمه في ثلاثة مواضع:

| الموضع | السطر |
|---|---|
| `services/contents/collection/view/index.js` | `const canDelete = !readonly && (_selectedCollection.delete ?? true);` |
| `services/contents/editor/toolbar.js` | `const canDelete = !(collection?._type === 'entry' && collection.delete === false);` |
| `components/workflow/workflow-entry-card.svelte` | `collection?._type === 'entry' ? collection.delete !== false : true` |

فالنتيجة: زر الحذف يُخفى في قائمة السجلات وفي شريط المحرر. لكن **الحد الصادق**:
هذا يمنع الحذف *من واجهة CMS* فقط. من يملك التوكن يستطيع حذف ملف عبر GitHub
مباشرة، أو عبر `createCommitOnBranch` — وGitHub ينفّذ ما يسمح به التوكن. الحماية
هنا تمنع الخطأ البشري، لا تمنع صاحب الصلاحية. (لا توجد حماية من الحذف على مستوى
الفرع في هذا المستودع: `rulesets` فارغة، والحماية الحقيقية هي قصر التوكن على
مستودع المسودات فقط.)

### التحقق من أسماء الحقول (لماذا كان `archived` قاتلًا)

Sveltia تتحقق من `view_groups` و`sortable_fields` **عند التحميل**، وتُبلّغ عن اسم
حقل غير موجود كـ**خطأ** لا تحذير:

```
parseCmsConfig → parseCollections → parseEntryCollection
  → checkViewOptions (services/config/parser/collections/views.js)
  → addMessage() بنوعه الافتراضي 'error'  (parser/utils/validator.js:30)
  → collectors.errors
  → initCmsConfig يرمي «Errors found in configuration»  (services/config/init.js:112)
  ⇒ صفحة الدخول تُستبدل بقائمة الأخطاء، ولا يُركَّب المحرر إطلاقًا.
```

مخطط JSON الرسمي **لا يكشف هذا**: `view_groups[].field` و`sortable_fields[]`
نصوص حرّة فيه، فيمرّ التحقق بالمخطط بينما اللوحة معطّلة. لذلك:

- `buildAdminConfig()` يرفض التوليد إن وُجد أي اسم غير مُعرَّف
  (`undefinedFieldReferences` في `src/media/cms-config.ts`)، فلا يُكتب ملف معطوب.
- `tests/admin-config.test.ts` يفحص الملف **المُلتزَم** لا المولّد فقط، ويفشل إن
  أُعيد الخطأ. (مُثبَت: إعادة `archived` تُفشل 5 اختبارات.)

**ما لا يُفحص عن قصد** لأنه لا يُفحص بأمان: `relation.value_field` و
`display_fields` قوالب لا مسارات حقول، و`summary`/`slug.template` كذلك،
والمسارات المتشعّبة (`images.0.file`) تُقارن بأسمائها العليا فقط. ومفاتيح Sveltia
الخاصة المسموح بها دون حقل (`_summary`, `_manual`, `slug`, `commit_author`,
`commit_date`) مسرودة صراحةً في `NON_FIELD_SORT_KEYS`.

### الحذف

لا يوجد أمر حذف في هذا الـPR. منطق «لا تحذف صورة مستخدمة» موجود ومُختبَر في
`src/media/references.ts` (`checkDeletion`): يرفض الحذف إذا كان أي درس يشير إلى
الملف، أو إذا كان أي سؤال اختبار يستخدمه كـ`sourceImage`، أو إذا كان الاسم غير
قانوني (يرفض التطبيع بدلًا من تنظيف اسم مشبوه).

## 5. التحقق من المستودع الخاص — ما يجب أن تفعله أنت

**Sveltia غير معتمدة حتى تنفّذ الخطوات التالية بنفسك.**

### 5.1 سكربت تحقق GitHub (على جهازك)

```bash
npm run admin:verify-github -- --repo calesteer-create/MATH_7th-drafts
# أو بلا إدخال تفاعلي:
read -rs PAT && printf '%s' "$PAT" | npm run admin:verify-github -- --token-stdin
```

- يطلب التوكن من طرفية **مخفية** (أو stdin). لا يُقرأ من `--token` ولا من ملف
  ولا من متغير بيئة، ولا يُطبع ولا يُكتب على القرص. النتيجة تُكتب في
  `admin-verification.json` (مستثنى من git) وتحوي الحكم فقط.
- يقبل `--repo` لمستودع غير الوجهة (لتجربة مستودع مُعاد تسميته)، لكنه **للقراءة
  فقط** حتى تتحقق كل الشروط معًا:
  1. الاسم الذي أجاب عنه GitHub هو نفسه المطلوب، و`private === true`؛
  2. `permissions.push === true` — أي **غائب** يُرفض، ولا يُفسَّر الغياب كسماح؛
  3. الفرع التجريبي ليس الفرع الافتراضي ولا `main`؛
  4. **دليل الغياب**: استعلام مباشر عن المرجع نفسه
     (`GET /git/ref/heads/{branch}`) يعيد **404 مؤكدًا**. أي خطأ آخر
     (401/403/5xx/شبكة/جسم ناقص) = «غير معروف» ⇒ **لا كتابة**. لا يُستخدم
     `GET /branches` لإثبات الغياب لأنه مُصفَّح وقد يفشل.
- **لا يُعتمد على بيانات مقروءة سابقًا**: قبل `createRef` مباشرة يُعاد قراءة
  بيانات المستودع من GitHub، ويُبنى دليل الوصول من هذا الرد **الطازج** لا من
  الرد الأول؛ ثم يُعاد فحص المرجع المحدد للفرع، ثم تُشغَّل نفس السياسة. إذا فشل
  هذا التحديث أو جاء ناقصًا أو باسم مستودع آخر أو بـ`private !== true` ⇒ **رفض**.
  نجاح قديم لا يُعتبر إذنًا بالمتابعة.
- الشروط كلها في دالة واحدة (`verifyWritePreconditions` في
  `src/media/repo-guard.ts`)، تُطبَّق في الـCLI **ومرة أخرى داخل
  `runSveltiaTrace` مباشرة قبل `createRef`** — لا طبقة واحدة، ولا استثناء.
- **يرفض أي مستودع لا يقول GitHub عنه `private === true`** — قبل إنشاء أي فرع
  أو commit، وقبل أي سؤال تأكيد. الرفض إلزامي ولا يغلبه `--yes` ولا أي خيار أو
  متغير بيئة (كل محاولات الالتفاف مغطاة باختبار). وجود `private` غائبًا أو بقيمة
  غير منطقية معاملته كـ«غير خاص».
- يرفض المستودع العام للموقع بالاسم أيضًا، ويرفض `main` والفرع الافتراضي.
- ينفّذ تسلسل Sveltia الحقيقي على **فرع مؤقت**: إنشاء الفرع → commit لملف
  فحص → محاولة ثانية بنفس `expectedHeadOid` (يجب أن تُرفض) → قراءة الملف
  للتأكد → حذف الفرع.
- رموز الخروج: `0` نجاح · `1` فشل الفحص · `2` رفض قبل أي كتابة · `3` الهدف
  ليس خاصًا · `4` تعذّر إثبات أن الفرع التجريبي غير موجود.

#### حدّ لا يستطيع GitHub نفسه تجاوزه

لا يوفّر GitHub نقطة نهاية للقراءة تُبلغ عن **الصلاحيات الفعلية** لتوكن
fine-grained. الحقل `permissions` في `GET /repos/{o}/{r}` يصف وصول
**المستخدم المصادَق** إلى المستودع (pull/push/admin)، وقد يُحسب أحيانًا وفق
صلاحيات التوكن نفسه — وهذا بالتحديد ما يجعل الاستدلال به غير موثوق. لذلك:

- `push: true` شرط **ضروري لا كافٍ**، ولا يجوز وصفه بأنه «تحقّق من صلاحيات
  التوكن».
- الإثبات الوحيد الصادق لـ`Contents: write` هو **كتابة يقبلها GitHub** أو يرفضها
  بـ403. لهذا يكتب الفحص في فرع مؤقت قابل للحذف فقط، ولا يلمس `main` أبدًا.
- إذا مرّ التوكن للقراءة فقط من الفحص المسبق (لأن `push` يصف المستخدم)، فإن
  `createRef` سيرفضه بـ403، ويُبلَّغ عن ذلك كفشل فحص مع نصيحة واضحة — لا
  كنجاح ولا كتحقق مسبق غير حقيقي.

- **ملكية الفرع**: لا يُحذف إلا فرع أثبت هذا التشغيل نفسه أنه أنشأه
  (`createRef` ناجح يُسجَّل فورًا)، وبشرط أن رأسه ما زال إما نقطة الإنشاء أو
  الـcommit الذي أنشأه التشغيل. فرع موجود مسبقًا يُرفض ولا يُمسّ ولا يُحذف،
  وفشل الإنشاء لا يؤدي إلى حذف أي فرع آخر. الاسم وحده ليس دليلًا على الملكية.
- إن فشل التنظيف: يتوقف، يطبع تقريرًا آمنًا (بلا توكن)، ويطلب منك فحص الفرع
  يدويًا قبل حذفه. لا يعيد المحاولة على عملية حذف.

### 5.2 تجربة الواجهة نفسها

1. أنشئ مستودع المسودات الخاص `MATH_7th-drafts` (لا أنشأته أنا).
2. أنشئ **Fine-grained PAT** مقصورًا على ذلك المستودع بصلاحية
   `Contents: Read and write` (و`Metadata: Read` تُضاف تلقائيًا). لا تشاركني إياه.
3. شغّل `npm run admin:verify-github` وارفع/احفظ الناتج عندك.
4. افتح النسخة الثابتة الخام محليًا: `npm run build:static && npm run preview:static` ثم
   `http://localhost:4173/MATH_7th/admin/`. (على خادم Next لا يوجد مسار `/admin/`
   للوحة Sveltia: الـmiddleware يحوّله إلى `/{locale}/admin` أي لوحة الخادم
   المختلفة. الصفحة الثابتة متاحة هناك على `/admin/index.html` فقط، وتقرأ
   الإعداد من `public/admin/config.yml` نفسه — وهو مناسب للفحص لا للتجربة الكاملة.)
   **هذا فحص محلي لـ`out/` الخام فقط.** خط النشر يشغّل `pages:prepare` الذي يستبعد
   `admin/` من `pages-dist/`، لذلك `/MATH_7th/admin/` على GitHub Pages يجب أن يُجيب
   404 ولا يُنشر محرر Sveltia في هذه المرحلة.
   سجّل الدخول بالتوكن، وافتح وحدة واحدة، **عدّلها واحفظها**.
5. تأكد أن commit ظهر في `MATH_7th-drafts` على `main`، وأن الصور وصلت WebP.
6. **تحقّق من القيمة المخزَّنة في `images[].file`**: المتوقع
   `/media/lessons/<id>/<file>.webp` (مسار، لا اسم مجرّد) — هذا سلوك Sveltia
   المثبت من مصدرها. ثم شغّل `npm run media:sync -- --dry-run` واقرأ سطر
   `→ canonicalise lesson <id>`: كل قيمة ستُطبَّع تُعرض قبل أي كتابة. بعد ذلك
   `npm run media:sync` ثم `npm run media:sync -- --check` على شجرة المسودات.
   إن ظهر `unrecognised image path` فالصورة ليست WebP أو في مجلد درس آخر: أعد
   رفعها ولا تُعدّل الاسم يدويًا. وإذا فشل التشغيل **قبل** مرحلة الكتابة (خطأ
   تحقق أو مسار غير معروف) فلن يكتب شيئًا إطلاقًا — لا JSON ولا مصغّرة. وإذا
   فشلت **الكتابة نفسها** بعد نجاح التحقق فالشكل يعتمد على نتيجة التراجع، واقرأ
   السطر الأخير حرفيًا:

   | آخر سطر | المعنى | ما تفعله |
   |---|---|---|
   | `the tree is unchanged.` | التراجع اكتمل: كل ما أُنشئ حُذف وكل ما استُبدل أُعيد | أعد التشغيل بعد معالجة السبب |
   | `⚠ ROLLBACK INCOMPLETE — …` | التراجع لم يكتمل: الشجرة قد تختلف عمّا كانت | **لا تعِد التشغيل** قبل فحص الملفات المذكورة في أسطر `✗ rollback:` أعلاه |

   وفي الحالتين يُطبع السبب الأصلي أولًا في سطر `✗ writing failed: …`.
7. عندها فقط: حدّث `ADMIN_STATUS.verifiedAgainstPrivateRepo` في
   `src/media/cms-config.ts` و`docs/ADMIN.md` بالتاريخ.

## 6. حدود الأمان — بصراحة

- **GitHub Pages لا يوفّر مصادقة خادمية.** لا شيء يحمي `/admin/` من الفتح؛
  الحماية الفعلية هي ألّا يملك أحد توكنًا صالحًا. من يملك التوكن يملك ما يملكه
  التوكن.
- **أي PAT يُستخدم من المتصفح يحمل صلاحياته الفعلية كاملة.** لهذا يجب قصره على
  مستودع المسودات وحده، وبأقصر مدة صلاحية تناسبك، وإبطاله عند الشك.
- التوكن يُخزَّن في `localStorage` للمتصفح (سلوك Sveltia). أي XSS في صفحة اللوحة
  أو إضافة متصفح خبيثة قد تصل إليه.
- **لا يوجد توكن في الكود ولا في المستودع**، ولا Secrets، ولا خدمات خارجية.
- **الحارس على مستوى الكود، لا الخادم.** GitHub ينفّذ ما يسمح به التوكن. لذلك
  القاعدة العملية: التوكن مقصور على مستودع المسودات وحده، وإلا فلا شيء يمنع
  كتابة يدوية إلى مستودع آخر. السكربت يرفض المستودع غير الخاص، لكنه لا يستطيع
  إلغاء صلاحية توكن أعطيته أنت صلاحية أوسع.
  تحقق آلي في `tests/no-public-write.test.ts`.
- الصفحة تُحمّل Sveltia من `unpkg` بإصدار مثبّت وبصمة SRI؛ أي تغيير في الـCDN
  يوقف التحميل بدلًا من تشغيل كود مختلف.
- الموقع العام (Pages) لا يعرض لوحة الإدارة في هذه المرحلة: `pages:prepare`
  يستبعد `admin/` من Artifact النهائي، و`pages:audit` يفشل إذا ظهر مسار إداري
  أو مرجع خادمي ممنوع. لذلك `/MATH_7th/admin/` على Pages يجب أن يُجيب 404.
  صفحة Sveltia التجريبية موجودة فقط في `out/` الخام للمعاينة المحلية، ولا تُرفع.

### 6.1 ما هو محمي بوصف ملفات، وما هو خارج هذا الضمان

الوسائط المرفوعة (كل قراءة/كتابة/حذف تحت `public/media`: `media:sync`،
`content:validate`، الاستيراد، واللوحة) تُفتح **نسبةً إلى واصف مجلد مُثبَّت**،
لا نسبةً إلى مسار نصي. النتيجة: تبديل مجلد برابط رمزي أثناء العمل لا يُقرأ ولا
يُكتب خارج الشجرة، لأن المسار النصي لا يُستخدم بعد فتح المجلد الأب.

هذه القائمة تحدّد بدقة ما **يبقى خارج** ذلك الضمان، ولا تُخفى:

| الحالة | لماذا بقيت |
|---|---|
| إنشاء جذر الوسائط نفسه (`ensureMediaRoot`) عبر `mkdirSync({recursive:true})` | الجذر اختاره المشغّل قبل أن يوجد أي واصف نُثبّت عليه؛ لا يوجد أب آمن نبدأ منه |
| قراءة محتوى المستودع (`content/units`, `content/lessons`, `content/quizzes`) عبر `readJsonDir`/`readLesson` | محتوى المستودع نفسه، لا وسائط مرفوعة؛ يُقرأ بمسار لأنه مصدر الحقيقة الذي يُراجعه git |
| الرابط الصلب (hard link) إلى inode داخل الشجرة باسم خارجها | لا يُتبع ولا يُمنع: الواصف يقرأ الـinode نفسه. لا يمنح قدرة جديدة، لكنه ليس ممنوعًا |
| تعديل ملف بعد فتح واصفه من عملية أخرى | الواصف يضمن *أي* inode، لا ثبات محتواه عبر الزمن |
| تعدد العمليات (`serialize()` داخل العملية الواحدة) | التزامن بين عمليات مختلفة ليس مُسلسَلًا |
| macOS/BSD | لديها `/dev/fd` لكن **غير مختبرة**؛ الضمان المُثبت هو Linux فقط |

ما أُغلق في هذه الجولة، بعد أن كان مفتوحًا:

| كان | صار |
|---|---|
| `fileExistsAt` تُعيد `false` لأي مدخل ليس ملفًا عاديًا (رابط، FIFO، مجلد) | تُعيد `false` للغياب (`ENOENT`) وحده؛ غير ذلك **رفض صريح** |
| `remember()` يسجّل المسار في `createdFiles` عند `false`، فيحذفه rollback لاحق | التسجيل يقع **فقط** بعد أن يُبلّغ `writeFileAt` أنه أنشأ الملف |
| `rollbackWrites` يرفض المجلدات فقط ويحذف ما عداها (ومنها الروابط) | يحذف **ملفًا عاديًا** فقط؛ الرابط وFIFO والجهاز رفض |
| `thumbExists` تبتلع كل خطأ وتُعيد "لا مصغرة" | يمرّر الرفض؛ `ENOENT` وحده يعني الغياب |
| جرد الـorphans في `content:validate` بـ`readdirSync(path)` يدخل مجلد درس عبر رابط | جرد عبر `OpenDir.list()` و`openDirUnder()`؛ الرابط يُتخطّى ولا يُتبع |
| فتح FIFO يعلّق العملية قبل `fstat` | `O_NONBLOCK` على كل فتح (`readFileAt`, `writeFileAt`, `readKey`, rollback, `import.ts`, `storage-safe`) |

وفي هذه الجولة:

| كان | صار |
|---|---|
| `writeFileInside` يفتح بلا `O_NONBLOCK` و**بلا `fstat`** قبل `ftruncate` | `O_NONBLOCK` على الفتحين، والترتيب: فتح ← `fstat` يثبت أنه ملف عادي ← `ftruncate` وكتابة. لا `O_TRUNC` في أي راية |
| `writeJson` يرفض الروابط فقط، فيستبدل FIFO/socket/جهاز بملف JSON عبر `renameat` | `lstat` قبل أي إنشاء أو استبدال؛ يُستبدل **ملف عادي** أو لا شيء. الأنواع الأخرى رفض وتبقى كما هي |

### ما لا يُثبته rollback (مهم)

الحذف في `rollbackWrites` يثبت **النوع** لا **الهوية**:

- **إثبات الإنشاء وقت الكتابة** — قائم: المسار يدخل `createdFiles` فقط بعد أن
  يُبلّغ `writeFileAt` أنه أنشأه (`O_EXCL` نجح).
- **إثبات هوية الملف وقت الحذف** — **غير قائم**: لا يُحفظ `dev`/`ino` للملف
  المُنشأ، فالاسم قد يشير إلى inode آخر. الملف العادي الذي يستبدل ملفنا بنفس
  الاسم **يُحذف**، ولا يُكتشف.

إغلاق هذه النافذة يحتاج حفظ واصف الملف (أو `dev`/`ino`) طوال الدفعة ومقارنته قبل
الحذف؛ Node لا يوفّر `unlink` مشروطًا بـinode، و`lstat` ثم `unlink` **لا يُغلق**
السباق لأن الاسم قد يُبدَّل بين النداءين — لذلك لم يُضَف، ولم يُدَّعَ.

النطاق محدود: الحذف محصور في `allowedRoots`، ولا يمسّ إلا **ملفًا عاديًا** في مسار
كتبه التشغيل، ولا يحدث إلا في rollback بعد فشل. وسلوك الاستبدال مثبّت باختبار
(`rollback deletion: type is proven, identity is documented as unproven`) حتى
تتغيّر الوثيقة إن تغيّر السلوك.

اختبارات هذه الجولة: `tests/media-pipeline.test.ts` (ملكية المدخلات ونوعها)،
`tests/content-model.test.ts` (جرد الـorphans عبر رابط)، `tests/images.test.ts`
(FIFO بلا تعليق)، `tests/media-sync.test.ts` (رابط في مكان المصغرة).

اختبارات هذا الضمان في `tests/media-sync.test.ts` (سباق `media:sync` نفسه مع
شاهد `atime`)، `tests/images.test.ts` (عدّ الواصفات في `/proc/self/fd`)،
و`tests/media-pipeline.test.ts` (ملكية الملف المؤقت، والاستعادة، وفحص مساحة
الأسماء).
